## 阅读说明与共同安全边界

- **owner / Worker**：负责管理一组下级执行资源的控制对象。本文件讨论同一个 owner 内的隔离，不代表所有独立 Worker 必须一起停止。
- **MPI group**：由一次 mpirun 启动和管理的一组 rank。A、B 表示两个不同 group；每个 rank 有自己的 `session_id`，不能将一个 rank 的身份当作整组身份。
- **新工作**：故障被观察并发布后，新进入的普通提交、控制或通信资源建立请求。清理、取消和释放不能因普通工作门禁而一律禁止。
- **事务**：为建立通信域而进行的 PREPARE_EXPORT、IMPORT、COMMIT、ABORT 过程。UD2 讨论已经开始但尚未完成提交的事务，不等同于已经运行的计算任务。
- **证明无关**：操作不依赖失效成员，且共享执行、通信和资源边界经验证允许隔离。仅看到 B 的进程还活着或状态为 ACTIVE，不足以证明 B 可以安全继续。

无论最终选择什么，都必须拒绝已识别失效成员的新授权及失效身份的 COMMIT，保留合法清理路径；无法证明故障可隔离时，按 owner 范围保守拒绝普通新工作。清理失败不能伪装成成功，资源也不能因身份失效就被视为已经释放。

本文件中的“继续”描述期望能力，不承诺未检测故障的瞬时发现、无中断执行、自动重试、原地恢复或热迁移。具体锁、缓存、版本字段与验证协议由 agent 设计。

### UD1 的场景与扩展选项

场景：同一个 Worker 已完成初始化，管理 MPI group A、B。A 的故障已被观察并发布；B 的成员与通信仍正常。是否能够证明 B 与 A 的故障无关，需要技术验证，不以“配置成两个 group”替代。

| 选项 | 期望行为 | 对修复范围的影响 |
| --- | --- | --- |
| UD1-A：owner 整体停止准入 | A 故障后停止该 Worker 的普通新工作，通过关闭并重建恢复 | Worker 级锁存是接受的策略；仍需修正确定的安全或清理缺陷 |
| UD1-B：支持无关 group 的新工作 | A 故障后，只有经证明不依赖 A 且可安全隔离的 B 工作仍能被接收 | 需设计操作依赖、group 局部故障和 owner 致命故障的区分，并验证共享执行与资源边界 |

易懂示例：A 负责一份计算、B 负责另一份计算。A 出问题后，是让这个控制对象暂停接收所有新任务，还是在证明安全后继续接收交给 B 的新任务？选择后者也允许 A 保持失效，不能推导出必须将 A 原地拉起。

边界说明：

- UD1-A 表示停止新工作准入，不等于立即杀死 B，也不自动定义所有已在执行任务的终止方式。
- UD1-B 不要求任意故障都能隔离；若共享 native 状态或资源受到影响，仍可停止整个 owner。
- 本项不自动承诺 A 原地重连、同一 MPI group 内部分 rank 存活或热迁移，也不保证已经开始的事务继续，后者见 UD2。
- 不能将初始化期间尚未 READY 的 group 当作运行中的健康 group，要求它承接新任务。

用户决定：采用 UD1-A；不新增 UD1-B 能力。

交付安排：当前 1.1 保留上述现有准入边界，不安排部分存活扩展。后续评审不得将缺少 UD1-B 能力作为本次必须修复的代码缺陷。

### UD2 的场景与扩展选项

场景：事务 T 只依赖 B，已经开始 PREPARE/IMPORT、尚未完成提交。另一项变化使全局 registry epoch 改变，但经验证 T 的成员与资源依赖仍然有效，且 owner 仍允许执行该事务。

这是未来事务关联设计中的期望行为选择。当前 `77b2f856` 的 `GlobalDomainCommand` 尚无 registry epoch 字段，不能将该场景描述为已经实现的事务版本拒绝行为。另一个 group 的失败是否仍允许 owner 执行 T，须先遵守 UD1。

| 选项 | 期望行为 | 对修复范围的影响 |
| --- | --- | --- |
| UD2-A：允许保守中止、重新发起 | 旧全局视图的 T 不继续提交；按协议处理已执行阶段并安全清理，满足准入条件后可重新发起 | 可采用严格全局版本绑定；不承诺自动重试，重试也不能绕过 owner 故障准入策略 |
| UD2-B：保留独立事务的进展 | 经证明依赖未变化且 owner 可用的 T 可以继续，无须仅因无关的全局版本变化而重做 | 需定义成员依赖和兼容性验证，不能仅比较同一个全局 epoch，也不能直接改写事务保存的版本 |

易懂示例：B 已经为通信准备好资源，正在等待最后确认。另一项无关变化让总目录版本变了。是否允许 B 撤销本次准备、之后重新申请，还是要求系统证明 B 未受影响后保留这次准备并继续？

边界说明：

- 若 T 实际包含失效成员、依赖已改变，或者无法证明兼容，UD2-B 也不能放行旧 COMMIT。
- 若部分节点已经提交，必须由事务协议处理其状态；“允许中止”不代表 ABORT 可以无条件撤销已完成的提交。
- 本项不决定历史已提交通信域是否继续可用，也不承诺正在执行的计算任务无中断。
- 注册组、STARTING、ACTIVE、关闭等版本变化应结合生命周期分析。仅列出 epoch 更新点，不能证明正常运行中的事务会受影响。

两项决策的关系：

| 组合 | 能力含义 |
| --- | --- |
| UD1-A + UD2-A | owner 故障后停止新工作，事务允许保守处理和重建 |
| UD1-B + UD2-A | 可接收健康 group 的新工作，但无关版本变化仍可要求旧事务重新发起 |
| UD1-B + UD2-B | 健康 group 的新工作和依赖未变的未完成事务均可在验证后继续 |
| UD1-A + UD2-B | owner 故障拒绝仍优先；事务继续能力只适用于 owner 未被故障门禁阻止的无关变化，不能用来绕过 UD1-A |

用户对是否要求 UD2-B 保留独立事务进展的决定：待明确；未将尚未完成的事务契约标为已经实现或已经验收。

若选择保留独立事务进展，其交付安排：待明确对应后续 1.4 的验收要求，及当前 1.1 需要保留的扩展接口；不在本文件代定具体实现。
